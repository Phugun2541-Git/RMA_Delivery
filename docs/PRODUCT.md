## 1. ภาพรวมระบบ
```
ลูกค้า ──┬─ แอป Delivery (โปรเจคนี้) ─┐
         ├─ Food Hub (เว็บ)           ├─→ Order core (server) ──┬─→ Smart Kitchen (ร้านที่ผูก: เข้าครัว + ตัดสต็อก)
         └─ LINE LIFF                 ┘                         └─→ แอป Delivery ฝั่งร้าน (ร้านที่ไม่ผูก)
ไรเดอร์ ── แอป Delivery ── รับงานจาก Order core        Admin ── เว็บ back-office (ยังไม่มีในแผน)
```
- ร้านมี 2 แบบ: **ผูก Smart Kitchen** (เมนู/สต็อกมาจาก SK · order วิ่งเข้าครัวเอง) กับ **ไม่ผูก** (จัดการเมนูในแอป · ไม่มีสต็อก มีแค่ขาย/หมด)
- **MVP = อาหาร + เรียกรถรับส่งคน** (D-010) · ภายหลัง = ส่งของ · บริการ (ซ่อมแอร์ แม่บ้าน) — ทุกแบบคือ "งาน" ที่มีผู้สั่ง ผู้ให้บริการ และสถานะ
- backend เป็นของทีมเดิม แอปนี้เป็น client อย่างเดียว (D-008) · แอปเดียว 3 role (D-009)

## 2. เมนูต่อ role (ตามที่เจ้าของให้มา + ที่ปรับ)
| Role | เมนู |
|---|---|
| ลูกค้า | หน้าหลัก (เลือกบริการ) · ตะกร้า · ประวัติรายการ · ข้อความ/แจ้งเตือน (แชทร้าน/ไรเดอร์) · ข้อมูลส่วนตัว + ที่อยู่ · ตั้งค่า · ศูนย์ช่วยเหลือ |
| ร้านค้า | order · เมนูอาหาร · ข้อมูลร้าน (เปิด/ปิด) · **เชื่อมต่อ Smart Kitchen** · การชำระเงินและบัญชี · รายงาน · ศูนย์ช่วยเหลือ/เคลม |
| ไรเดอร์ | งานปัจจุบัน · ประวัติงาน · รายได้ · รายงาน · ข้อมูลส่วนตัวและรถ · ศูนย์ช่วยเหลือ |

**ปรับจากโจทย์:** "เชื่อมต่อ Smart Kitchen" ถูกเขียนไว้ใต้เมนูลูกค้า แต่เนื้อหาเป็นของร้านค้า → ย้ายไปฝั่งร้าน (`M-10`)

## 3. สถานะ order อาหาร (ร่าง — ต้องเคาะกับทีม backend/Smart Kitchen)
```
รอชำระ → รอร้านรับ → ร้านกำลังทำ → พร้อมส่ง → ไรเดอร์รับของแล้ว → กำลังส่ง → ส่งสำเร็จ
   │          │            │                                                └→ มีปัญหา (เคลม)
   └→ หมดเวลา └→ ร้านปฏิเสธ └→ ยกเลิก (ใครยกเลิกได้ถึงขั้นไหน + คืนเงินยังไง = กฎธุรกิจที่ยังไม่มี)
```
การหาไรเดอร์เดินคู่ขนาน (เริ่มหาตอนร้านรับ หรือใกล้ทำเสร็จ) · หาไรเดอร์ไม่ได้ต้องมีทางออก

## 4. สิ่งที่โจทย์ยังไม่มี แต่ระบบแบบนี้ขาดไม่ได้
| # | เรื่อง | ทำไมขาดไม่ได้ |
|---|---|---|
| 1 | **Admin back-office (เว็บ)** | อนุมัติร้าน/ไรเดอร์ · ตั้งค่าส่ง/GP/โปร · จัดการเคลม คืนเงิน · แชทช่วยเหลือ — ไม่มีสิ่งนี้เปิดบริการไม่ได้ |
| 2 | การสมัคร + ตรวจเอกสารร้าน/ไรเดอร์ (KYC) | ต้องรู้ตัวตนคนรับเงินและคนส่งของ |
| 3 | สูตรเงิน: ค่าส่ง · GP ร้าน · ส่วนแบ่งไรเดอร์ · รอบโอน · เงินสดปลายทางที่ไรเดอร์ถือ | หัวใจของธุรกิจ และเป็นส่วนที่พลาดแล้วเสียหายที่สุด |
| 4 | กฎยกเลิก/คืนเงิน/เคลม | ใครยกเลิกได้ถึงขั้นไหน ใครรับผิดชอบค่าอาหารที่ทำแล้ว |
| 5 | การจ่ายงานให้ไรเดอร์ (dispatch) | ยิงให้คนใกล้สุด หรือ broadcast · หมดเวลารับงานแล้วทำไง · รับหลายงานพร้อมกันได้ไหม |
| 6 | Real-time: push notification · สถานะ order · พิกัดไรเดอร์ · แชท | แอปนี้ไม่มีความหมายถ้าต้องกด refresh |
| 7 | Login ด้วย OTP + ซ่อนเบอร์จริง (โทร/แชทในแอป) | ยืนยันเบอร์ และกันเบอร์ลูกค้า-ไรเดอร์รั่วถึงกัน |
| 8 | PDPA consent + ลบบัญชีได้ในแอป | กฎหมายไทย และเป็นเงื่อนไขของ App Store / Play Store |
| 9 | ตัวเลือกเมนู (ท็อปปิ้ง ระดับเผ็ด) · เวลาเปิดปิด · พื้นที่ให้บริการ | ไม่มี = สั่งอาหารจริงไม่ได้ |
| 10 | คะแนน/รีวิว · โค้ดส่วนลด · หลักฐานการส่ง (รูป) | ควบคุมคุณภาพ + ดึงผู้ใช้ + กันข้อพิพาท |
| 11 | ต้นทุน Google Maps / SMS OTP / payment gateway ต่อ order | คิดตามจำนวนครั้ง — ต้องรู้ก่อนออกแบบว่าเรียกบ่อยแค่ไหน |

## 5. จุดเด่นที่เจ้าอื่นทำได้ยาก (เพราะเรามี Smart Kitchen)
| # | ไอเดีย | ได้อะไร |
|---|---|---|
| 1 | **สต็อกจริงจากครัว** — เมนูหมดใน SK = หมดในแอปทันที | ลด order ที่ถูกยกเลิกเพราะของหมด (ปัญหาที่ลูกค้าเกลียดที่สุด) |
| 2 | **เวลาเตรียมจากคิวครัวจริง** → เรียกไรเดอร์ให้มาถึงพอดีอาหารเสร็จ | ไรเดอร์ไม่ต้องรอ · อาหารไม่เย็น · ETA แม่น |
| 3 | **สั่งล่วงหน้าแล้วไปกินที่ร้าน / รับเอง** (SK มีโต๊ะอยู่แล้ว) | ช่องทางที่ไม่ต้องใช้ไรเดอร์ = GP ต่ำ |
| 4 | **สะสมแต้มข้ามหน้าร้านกับ delivery** บัญชีเดียว | ร้านได้ลูกค้าประจำ ไม่ใช่แค่ยอดจากแพลตฟอร์ม |
| 5 | **ร้านไม่ต้องมีแท็บเล็ตเพิ่ม** — order เข้าจอครัวเดิม | เหตุผลที่ร้านใน SK จะเลือกเราก่อนเจ้าอื่น |
| 6 | **สั่งผ่าน LINE ไม่ต้องลงแอป** (LIFF) + แจ้งสถานะทาง LINE | ลดแรงเสียดทานของลูกค้าใหม่ในไทย |
| 7 | บริการหลายอย่างในบัญชีเดียว (อาหาร + แม่บ้าน + ซ่อม) | ฐานลูกค้าเดียว ใช้ซ้ำข้ามบริการ |

## 6. ข้อเสนอเรื่อง Food Hub ซ้ำกับแอปนี้
มอง Food Hub เป็น **ช่องทางเว็บของระบบเดียวกัน** ไม่ใช่ระบบคู่ขนาน: order core + เมนู + บัญชีลูกค้าอยู่ที่เดียว
แอป / เว็บ / LIFF เป็นแค่หน้าบ้านคนละแบบ — ถ้าแยก 2 ระบบจะมีเมนู 2 ชุด ลูกค้า 2 ฐาน และร้านต้องดู order 2 ที่
